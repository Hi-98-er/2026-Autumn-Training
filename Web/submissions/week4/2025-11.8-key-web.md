反序列化漏洞与 Java 利用链：从原理到 CTF 实战

一、反序列化漏洞通用知识点总结

1.1 本质

序列化是把对象转换为可存储或传输的字节流；反序列化是把字节流还原为对象。反序列化漏洞的核心问题在于：当应用信任并还原了攻击者可控的字节流时，还原过程本身就可能被滥用。OWASP 的定义直指要害：不安全反序列化产生于“不可信数据被用来滥用应用反序列化过程的逻辑”，攻击者可以借此执行代码、操纵对象或实施注入。

1.2 与 JSON/XML 的关键区别

JSON、XML 是数据描述格式，只传递值，不决定“实例化哪个类”。而 Java 原生序列化、Python pickle、PHP serialize 等原生序列化机制在流中编码了类型信息，反序列化器会根据流中的类名去加载并实例化任意可用的类，并在过程中触发该类的生命周期钩子。危险恰恰来自这个“类型自描述”特性。

1.3 危害层次

层次 表现
拒绝服务 构造深层嵌套或超大对象图，耗尽 CPU/内存
访问控制绕过 篡改序列化对象中的身份、权限字段
远程代码执行 通过 gadget chain 串联库类的副作用，最终调用 Runtime.exec 或 JNDI 注入

OWASP 明确指出，不安全反序列化可导致 DoS、访问控制问题和 RCE。

1.4 防御的根本原则

最安全的做法是永远不对不可信来源的数据执行原生反序列化。若无法避免，至少应当：使用数字签名/HMAC 保证完整性；在 ObjectInputFilter 中严格限制允许反序列化的类；将反序列化逻辑运行在隔离进程或沙箱中。用 JSON 等数据格式替代原生序列化是更彻底的方案，但要注意 Jackson 的 enableDefaultTyping 会把“由流决定类名”的问题重新引入。

二、Java 反序列化的核心机制

2.1 入口：readObject() 是攻击面

ObjectInputStream.readObject() 会在还原对象时，自动调用目标类中定义的 private void readObject(ObjectInputStream)（如果存在）。JVM 不会等待业务代码“使用”这个对象——对象一被重建，readObject 就已经执行完毕。这意味着攻击载荷在应用拿到对象之前就已经生效。

2.2 Gadget Chain：用“正常类”做“危险事”

Gadget chain（利用链）的精髓在于：攻击者不需要目标 classpath 中存在恶意类。他们只需要找到若干普通库类，这些类在反序列化过程中会自动调用某些方法（readObject、readResolve、hashCode、toString、get 等），并且这些方法的副作用可以被串联，最终抵达一个“执行原语”（Runtime.exec、JNDI lookup、defineClass 等）。ysoserial 把这些链工程化，覆盖 Apache Commons Collections、Spring、Groovy 等常见库。

2.3 CC1 与 CC6：理解“触发入口”的可替换性

CC1 的经典路径是：

```
AnnotationInvocationHandler.readObject()
  → TransformedMap 的 entrySet 遍历
  → setValue()
  → ChainedTransformer.transform()
  → InvokerTransformer 反射调用 Runtime.exec()
```

后半段的 ChainedTransformer + InvokerTransformer 是执行核心，前半段是“触发入口”。JDK 8u71 修改了 AnnotationInvocationHandler.readObject 的逻辑，CC1 随之失效。CC6 的应对方式极其简洁：保留执行链，换掉触发入口。它改用 HashSet.readObject() → HashMap.hash() → TiedMapEntry.hashCode() → LazyMap.get() 来触发 transform()，因为 HashSet 的 readObject 在任何 JDK 版本下都会走到 hashCode()。这个思路本身就是 Java 反序列化利用中最重要的方法论：链是可以拆装的，入口不通就换入口，执行原语不变。

三、三道 CTF 题目的解题过程与解法

题目一：长城杯 2022 b4bycoffee —— 黑名单绕过 + 自定义 Sink

题目概况：Spring Boot 应用，POST /b4by/coffee 对 JSON 字段 venti 做 base64 解码后交给自定义 AntObjectInputStream.readObject() 反序列化，结果强转为 Venti。

防御：AntObjectInputStream.resolveClass() 维护了 5 个类名的黑名单：BadAttributeValueExpException、ROME ObjectBean/ToStringBean、TemplatesImpl、Runtime。经典的 BadAttributeValueExpException 入口和 TemplatesImpl 执行原语被同时封堵。

突破点：ROME 库的 EqualsBean 不在黑名单中。EqualsBean.hashCode() 会调用 beanHashCode()，进而调用 this.obj.toString()。而题目自定义的 CoffeeBean 实现了 Serializable，其 toString() 方法执行 defineClass + newInstance()，本身就是执行原语。

利用链：

```
HashMap.readObject()
  → hash(key)
  → EqualsBean.hashCode()
  → beanHashCode()
  → CoffeeBean.toString()
  → defineClass(Evil).newInstance()
```

Payload 构造的关键细节：题目作者在生成器中将 ClassByte 先设为无害的 Dummy.class，因为本地 map.put() 在序列化之前就会触发 hashCode → toString → defineClass；直接放入 Evil 字节码会在本地执行。反射替换为真实 Evil 字节码后，再执行序列化输出。Evil 类通过 Spring 的 RequestContextHolder.currentRequestAttributes() 获取当前 HTTP 响应，将 flag 直接写回响应体，实现带内外带。

解法评价：这道题的设计意图很清晰——逼迫解题者从题目自身提供的类中找 sink。黑名单封住了“经典链”，但 CoffeeBean 的 toString 被刻意暴露为一个可达的 defineClass 入口。如果解题者只会在 ysoserial 里换 payload，这道题就无解；必须回到代码审计，审视“题目给了我什么类”。这是 Java 反序列化 CTF 中非常典型且合理的出题方式。预置 Dummy.class 的细节也说明作者对“payload 生成过程中的本地触发”有实战意识，避免了生成器自身被反噬。

题目二：bypassit-rasp-bypass —— RASP 拦截下的链替换

题目概况：POST /bypassIt 直接使用 ObjectInputStream.readObject() 反序列化请求体，但部署了定制 RASP。拦截规则为：TemplatesImpl.getStylesheetDOM() 直接返回 null；AccessibleObject.setAccessible0(boolean) 被置为 no-op。

后果：CommonsCollections 系列依赖 setAccessible 反射修改字段，TemplatesImpl 链依赖 getStylesheetDOM/newTransformer 路径，两条主流路线同时被封死。

突破思路：题目要求解题者找到一个既不触碰 TemplatesImpl、也不调用 setAccessible 的链。最终构造为：

```
BadAttributeValueExpException.readObject()
  → val.toString()   [val = POJONode(JdbcRowSetImpl)]
  → POJONode.toString()
  → Jackson ObjectMapper.writeValueAsString(JdbcRowSetImpl)
  → 调用所有 public getter
  → getDatabaseMetaData()
  → connect()
  → InitialContext.lookup("ldap://...")
  → JNDI 注入 → RCE
```

JdbcRowSetImpl 的 getDatabaseMetaData() → connect() → JNDI lookup 是 JDK 内置行为，完全不需要反射修改访问权限；Jackson 对 POJONode 的序列化通过 public getter 进行，绕开了 setAccessible0。

解法评价：这道题的价值在于展示了 RASP/黑名单防御与 gadget 选择之间的博弈。很多 writeup 在遇到 setAccessible 拦截时第一反应是去找“另一个需要 setAccessible 的链”，但真正的出路是换执行原语类别：从“反射修改字段”转向“JNDI 注入”，从“TemplatesImpl 字节码”转向“public getter 副作用”。BadAttributeValueExpException 在 b4bycoffee 中被黑名单封禁，在这里却是可用的入口——同一个类在不同防御配置下的可用性可以完全翻转，这是 Java gadget 利用的常态。

题目三：ISCTF Regretful_Deser —— 二次反序列化 + JRMP 的迂回

题目概况：JDK 1.8.0_472，Hibernate 5.6.15.Final 依赖。入口存在 hashcode 匹配要求，需传入与 n1ght 不同但 hashcode 相同的字符串。黑名单禁用 org.apache.commons.collections（封 CC 链）、com.sun.org.apache.xalan（封 TemplatesImpl.getOutputProperties）、javax.swing（封 EventListenerList 入口）。

预期方向：Hibernate 链最终触发 GetterMethodImpl.get()，到达一个 getter 调用点。黑名单的目的正是让解题者无法直接用 CC 或 TemplatesImpl 从 getter 走到执行。解题者需要利用“二次反序列化”来绕过黑名单：外层反序列化触发一个 getter，该 getter 内部再次执行反序列化，而第二次反序列化不受题目 resolveClass 黑名单的约束。

转折：高版本 JDK 下 LDAP 远程 codebase 加载被限制，RMI/JNDI 常规路径不通。解题者转向 JRMP：利用 ActivatableRef 的无参 getRef() 方法，它与有参 invoke() 最终走到同一个 activate 路径；将 Activator 设为动态代理对象，调用其 activate() 时转发到 RemoteObjectInvocationHandler.invoke()，进而触发 JRMP 反序列化，在 executeCall 中完成二次反序列化。

解法评价：这是一道难度明显更高的题。前两道题的“绕过”发生在类名层面（换一个不在黑名单里的类），这道题的绕过发生在协议和阶段层面：黑名单只拦第一层反序列化的类名，二次反序列化在另一个上下文里执行，黑名单自然失效。选择 JRMP 而非 LDAP，也说明解题者对高版本 JDK 的限制有清醒认识。一个值得注意的细节是，解题者最初面对 getter 触发点与 ActivatableRef.invoke 的有参/无参不匹配问题，最终通过无参的 getRef 找到了出路——这种从“参数签名不匹配”中发现替代方法的调试能力，是这道题真正的分水岭。

四、对别人解法的看法与总结

4.1 三种解法的层次差异

b4bycoffee 的解法是 “读题目给的代码” ：当通用链被封，答案往往就在题目自定义的类里。这不是“非预期”，而是出题人有意留的门。bypassit 的解法是 “换执行原语类别” ：不跟 RASP 在同一个维度上对抗，而是选择一条 RASP 没有覆盖的路径（JNDI + public getter）。Regretful_Deser 的解法是 “换攻击阶段” ：黑名单只作用于第一层 resolveClass，二次反序列化把战场转移到了黑名单够不到的地方。三者分别对应 Java 反序列化 CTF 中最常见的三种突围思路：从题目自身找类、从执行原语找替代、从反序列化层次找盲区。

4.2 值得警惕的写法

一些 writeup 在 b4bycoffee 这类题上容易陷入“先跑 ysoserial，失败后直接判定不可做”的误区。实际上，黑名单的检测时机（resolveClass 只检查流中出现的类名）和检测范围（是否检查 byte[] 字段内部的字节码）之间存在结构性缝隙，b4bycoffee 的 CoffeeBean 正是利用了这个缝隙：CoffeeBean 的类名不在黑名单中，恶意字节码藏在它的 byte[] 字段里，resolveClass 根本不会解析到。理解“黑名单检测的是什么、不检测什么”，比记住更多链更重要。

4.3 防御视角的启示

从防守方看，这三道题恰好暴露了逐类黑名单的固有缺陷：你永远可能漏掉一个类（b4bycoffee 的 EqualsBean），你永远可能漏掉一种执行原语（bypassit 的 JNDI），你也永远可能漏掉一个反序列化层次（Regretful_Deser 的二次反序列化）。Java 官方给出的方向是 ObjectInputFilter 的允许列表而非黑名单——只允许确实需要反序列化的少数类通过，其余一律拒绝。在 CTF 语境下，黑名单是出题人控制难度的手段；在真实防御中，它几乎注定是不完备的。
